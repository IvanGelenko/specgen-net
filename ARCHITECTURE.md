# PipingSpecPlugin (.NET) — Технологии и архитектура

> Версия 1.1.19 · AutoCAD Plant 3D 2026 (R25.0) · .NET 8
> Документ описывает фактическое состояние кода в репозитории, а не план.

---

## 1. Назначение

Нативный плагин AutoCAD Plant 3D, который генерирует спецификацию
трубопроводов (ведомость изделий и материалов по ГОСТ) из активного
проекта Plant 3D и выводит результат в документ Word (`.docx`) на основе
пользовательского шаблона.

Ключевые архитектурные решения:

- **Источник данных** — живая модель Plant 3D через `PnP*Mgd` API,
  а не SQLite-снимок `Piping.dcf`. Благодаря этому плагин видит
  несохранённые правки (читает in-memory активного документа +
  side-DB остальных чертежей).
- **Кнопка на ленте** регистрируется программно, без `.cuix`.
- **Среда выполнения** — внутри процесса AutoCAD.

---

## 2. Технологический стек

### Платформа и среда

- **Целевой фреймворк:** `net8.0-windows`. AutoCAD 2026 перешёл с
  .NET Framework 4.8 на .NET 8 — управляемые обёртки (`AcCoreMgd`
  Version 25.1.0.0) ссылаются на `System.Runtime 8.0.0.0`. Любая более
  старая версия падает на `CS1705` при компиляции или
  `FileLoadException` при загрузке.
- **Платформа:** только x64.
- **Тип сборки:** библиотека классов (DLL), загружается в AutoCAD
  через `NETLOAD` или AutoLoader-бандл.
- **UI-стек:** WPF (`UseWPF`) + Windows Forms (`UseWindowsForms`) —
  WPF для окон выбора и прогресса, WinForms для системных диалогов
  (`SaveFileDialog`, `MessageBox`).
- **Язык:** C# (`LangVersion=latest`), `Nullable` отключён.

### Внешние зависимости

- **DocumentFormat.OpenXml 2.20.0** (NuGet) — запись `.docx`. Намеренно
  остаётся на ветке 2.x: 3.x убрала legacy-API, которые здесь нужны.
  `CopyLocalLockFileAssemblies=true` гарантирует, что эта DLL копируется
  рядом с плагином, чтобы AutoCAD смог её разрешить при загрузке.
- **System.Text.Json** (из .NET BCL) — сериализация настроек.

### Ссылки на AutoCAD / Plant 3D (все `Private=False` — не копируются)

| DLL | Расположение | Назначение |
|---|---|---|
| `AcCoreMgd`, `AcDbMgd`, `AcMgd` | корень AutoCAD 2026 | ядро AutoCAD .NET API |
| `AdWindows` | корень AutoCAD | лента (`Autodesk.Windows.RibbonControl`) |
| `PnP3dMain`, `PnP3dProjectPartsMgd`, `PnP3dObjectsMgd` | `\PLNT3D\` | объекты и проектные части Plant 3D |
| `PnPProjectManagerMgd` | `\PLNT3D\` | `PlantApplication.CurrentProject`, `PlantProject` |
| `PnPDataLinks`, `PnPDataObjects` | корень AutoCAD | `DataLinksManager`, доступ к данным |

> ⚠ `PnP.dll` — нативный ARX без управляемых метаданных. Никогда не
> добавлять его в ссылки из C#.

### Тесты и инструменты

- **xUnit** — модульные тесты в `test/PipingSpecPlugin.Tests`
  (логика `SpecRowBuilder`, `PipeBendFolder`, `ScanCache`,
  `ValveCompanionFinder` — всё, что не требует живого AutoCAD).
- **`tools/reflect`** — вспомогательная консольная утилита для
  reflection-инспекции управляемых API Plant 3D при разведке.

```

│   │   ├── PartReader.cs            ← чтение данных из Plant 3D
│   │   ├── PartRecord.cs            ← сырая строка детали
│   │   ├── ScanCache.cs            ← кэш сканирования на сессию
│   │   ├── PipeBendFolder.cs        ← сворачивание гибов в трубу

│   │   ├── SpecRowBuilder.cs        ← агрегация PartRecord → SpecRow
│   │   ├── SpecRow.cs              ← строка спецификации

│   │   ├── ProjectFacts.cs          ← факты для чекбоксов picker'а
│   │   └── SpecConstants.cs         ← сентинелы, русские метки, порядок категорий
│   ├── Settings/
│   │   ├── PluginSettings.cs        ← настройки (%APPDATA%\...\settings.json)
│   │   └── RunLogger.cs            ← лог прогона (last-run.log)
│   ├── UI/
│   │   ├── SpecPickerWindow.xaml(.cs)  ← окно выбора фильтров
│   │   └── ProgressWindow.xaml(.cs)    ← модальный прогресс сканирования
│   └── Resources/                   ← icon16.png, icon32.png (EmbeddedResource)
├── test/PipingSpecPlugin.Tests/     ← xUnit-тесты
└── tools/reflect/                   ← reflection-утилита для разведки API
```

**Принцип слоёв:** папка `Spec/` не зависит ни от UI, ни от AutoCAD-команд
напрямую (кроме `PartReader`, которому нужен `Database`/`DataLinksManager`).
Это и позволяет покрыть бизнес-логику модульными тестами без живого AutoCAD.

## 4. Точки входа

| Команда | Класс | Что делает |
|---|---|---|
| `WRITESPEC` | `WriteSpecCommand.Run` | основной поток, область берётся из настроек |
| `WRITESPECPROJ` | `WriteSpecCommand.RunProject` | принудительно весь проект (кнопка «Весь проект») |
| `WRITESPECDWG` | `WriteSpecCommand.RunDrawing` | принудительно активный чертёж (кнопка «Текущий чертёж») |

Все три помечены `[CommandFlags.Session]` (работа на уровне сессии, а не
документа — нужно для side-открытия чертежей).

Регистрация в `AssemblyInfo.cs`:
- `[assembly: CommandClass(typeof(WriteSpecCommand))]` — где искать команды.
- `[assembly: ExtensionApplication(typeof(PluginBootstrap))]` — что
  вызвать при загрузке.

> Ранние диагностические команды (`PSPING`, `LISTPARTS`, `GENSPEC`,
> `SPECUI`, `LISTPROJECT`), упомянутые в README, **удалены** из
> production-сборки — осталась только генерация спецификации.

### Регистрация ленты (`PluginBootstrap`)

AutoCAD вызывает `IExtensionApplication.Initialize()` один раз при
загрузке сборки. Плагин:
1. Подписывается на `ComponentManager.ItemInitialized` — чтобы
   пересоздать вкладку, если её сбросит смена рабочего пространства.
2. Строит вкладку **«Спецификация»** с панелью из двух кнопок:
   «Весь проект» → `WRITESPECPROJ`, «Текущий чертёж» → `WRITESPECDWG`.
3. Иконки грузятся из встроенных ресурсов (`icon32.png`); при отсутствии
   кнопка остаётся текстовой, а не падает.

Кнопки маршрутизируют клики через минимальный `RelayCommand : ICommand`,
который вызывает `SendStringToExecute(команда)` — то есть кнопка просто
запускает соответствующую AutoCAD-команду.

## 5. Конвейер генерации спецификации

Полный поток в `WriteSpecCommand.RunCore` — одно нажатие кнопки:

```
[1] Проверки         → есть ли открытый проект Plant 3D? открыт ли чертёж (для dwg)?
        ↓
[2] Подготовка диска → автосохранение активного документа; закрытие/переоткрытие
                       фоновых документов с несохранёнными правками
                       (чтобы их данные оказались на диске для side-чтения)
        ↓
[3] Сканирование     → ScanWithCache → CollectFromProject → ReadOneDrawing → PartReader
     (ProgressWindow)   • список DWG из поддерева "Plant 3D Models"
                        • каждый читается как side-Database с диска
                        • кэш на сессию (ScanCache), если нет открытого документа
        ↓ ScanResult { records, activeDwgRecords, ownedPnPIds, topology }
[4] Анализ топологии → ValveCompanionFinder.Discover (ответные фланцы арматуры)
                     → PipeBendFolder.Fold (метры гибов → соседняя труба)
        ↓
[5] Picker           → ProjectFacts питают чекбоксы; пользователь выбирает
     (SpecPickerWindow)  статусы / категории / линии и правила исключения
        ↓ SpecPickerResult
[6] Фильтр области   → scope=dwg сужает records по SourceDwgPath (НЕ по PnPID)
        ↓
[7] Агрегация        → SpecRowBuilder.Build → List<SpecRow>
        ↓
[8] Запись           → AskOutputPath → SpecTemplateWriter.Write → .docx
        ↓
[9] Сохранение prefs → PluginSettings.Save (только при успехе) → открыть в Word
```

Каждый шаг логируется в `%APPDATA%\PipingSpecPlugin\last-run.log` через
`RunLogger` — короткий вывод в командную строку, полный трейс в файл для
поддержки.

## 6. Слой доступа к данным (`PartReader`)

Самый «хитрый» и тонко настроенный код — извлечение деталей из чертежа.

### Откуда берутся данные

- `DataLinksManager.GetManager(db)` → `SelectAcPpRowIds(db)` даёт rowId
  каждого `EngineeringItem`.
- `GetAllProperties(rowId, true)` возвращает мешок свойств (≈90 полей),
  которые мапятся в `PartRecord` по имени. Список свойств приводится к
  словарю один раз — O(1) вместо 35+ линейных проходов на строку.
- Дополнительно сканируется ModelSpace на предмет несохранённых
  Plant 3D-объектов (`FindAcPpRowId` по сущностям с классом `AcPp*`).

### Ключевые приёмы и подводные камни

- **`WorkingDatabase` swap.** `GetRelatedRowIds` на side-DB резолвит
  данные через нативный слой, привязанный к `HostApplicationServices.
  WorkingDatabase`. На время чтения рабочая БД переключается на читаемую,
  иначе `RowNotInThisDatabase`.
- **Принудительный сброс кэша.** Перед запросом вызывается серия
  `AcceptChanges` / `AuditDrawing` / `ReloadLinkMap` / `AuditLinks` /
  `RefreshLinkMap` (и аналоги на `PnPDatabase`) — разные версии Plant 3D
  отдают «свежесть» через разные API, поэтому это «belt-and-braces».
- **Живой тег линии (`ResolveLiveLineTag`).** Свойство `LineNumberTag` в
  детали копируется на момент привязки и не обновляется при переименовании
  линии. Реальный тег читается через `P3dLineGroupPartRelationship` →
  строку `P3dLineGroup` (с предпочтением project-DLM). Кэшируется по
  rowId LineGroup.
- **Топология (`BuildTopology`).** Через `ConnectionManager.GetConnections`
  для каждой сущности строится граф «деталь ↔ деталь» по прямым
  `P3dPartConnection`. Используется `GetConnections` (прямые рёбра), а
  **не** `ConnectionIterator` (он давал транзитивное замыкание и ложные
  срабатывания в детекторе ответных фланцев).
- **Оборудование и штуцера.** `Runtime.IsPnP3dEquipment` /
  `IsPnP3dNozzleSubPart` / `IsPnP3dConnector` помечают детали, «принадлежащие»
  оборудованию (штуцера, люки), чтобы исключить их из трубопроводной
  спецификации.

### Почему всегда читается с диска

`ReadOneDrawing` всегда открывает чертёж как side-Database с диска, даже
для активного документа. Причина: даже после `QSAVE` in-memory DLM-кэш
остаётся устаревшим и не отражает новые элементы. Поэтому шаг [2]
гарантирует, что последняя версия лежит на диске до сканирования.

## 7. Доменная логика

### `PipeBendFolder` — сворачивание гибов

Гибы трубы (`PipeBend`) физически — отдельные элементы, но в
закупочной спецификации их длина должна войти в соседнюю прямую трубу.
`Fold` находит соседний `Pipe` через граф топологии (предпочитая трубу с
тем же тегом линии, при необходимости — через хоп через коннектор-сварку)
и возвращает: какие гибы «съесть» + сколько метров добавить какой трубе.
Считается на **проектном** наборе записей до фильтра области — иначе гиб
на одном листе не нашёл бы свою трубу на другом.

### `ValveCompanionFinder` — спутники арматуры

Обходит граф `Арматура → Коннектор → Фланец`, находит ответные фланцы, а
для каждого — ближайшую прокладку и комплект болтов (по 3D-расстоянию;
порог 100 мм / 4″; fallback по `Spec + NominalDiameter + LineTag`).
Исключаются только при включённой опции «Исключать спутники арматуры».

### `SpecRowBuilder` — агрегация (ядро бизнес-логики)

Превращает сырые `PartRecord` в готовые `SpecRow`. Конвейер фильтров
(каждый отсев считается в `DropReasons` для диагностики):

1. свёрнутые гибы → `pipe-bend-folded`
2. фильтр по статусу
3. детали, принадлежащие оборудованию
4. спутники арматуры (опционально)
5. категория = Equipment (опционально)
6. коннекторы/сварка (опционально)
7. штуцера оборудования — **всегда**
8. пустая категория
9. фильтр по выбранным категориям
10. фильтр по выбранным линиям
11. **дедуп по `PnPID`** (деталь может быть в нескольких линиях —
    считается раз, с предупреждением)
12. трубы нулевой длины

Затем агрегация в «бакеты» по ключу `BucketKey`
(категория, имя, ND, ед., материал, тип/марка, код, производитель, линия).
Особенности:

- **Трубы** суммируют длину (с приведением единиц к метрам), плюс
  метры свёрнутых гибов; «осиротевшие» метры (труба-цель отфильтрована)
  переносятся на трубу-сиблинг той же линии.
- **Болтовые комплекты** учитывают `NumberInSet` (8 болтов = qty 8),
  вес делится на количество для веса 1 шт.
- **Контроль веса.** Если в группе вес отличается >5%, выводится
  предупреждение и берётся среднее.
- **Длина труб** округляется вверх до 0.1 м + примечание «с учётом 10% запаса».
- **Сортировка:** линия → порядок категорий (`CategoryOrder`) → ND по
  возрастанию → имя.

`DisableElementGrouping` добавляет `PnPID` в ключ бакета — каждый элемент
выводится отдельной строкой без агрегации.

### `SpecConstants`

Сентинелы (`__NULL__`, `__NO_LINE__`), русские метки категорий,
канонический порядок категорий, ключевые слова коннекторов, заголовок
секции шаблона `«Изделия и материалы»`. Строки заголовков секций должны
совпадать с текстом шаблона `.docx` дословно — по ним writer находит
таблицу для заполнения.

## 8. Вывод в Word (`SpecTemplateWriter`)

Запись поверх **пользовательского шаблона** через OpenXml — шаблон
никогда не перезаписывается (сначала `File.Copy`). Алгоритм:

1. найти таблицу, где есть одноячеечная строка-заголовок
   «Изделия и материалы» (нечёткое сравнение — допускает номера секций);
2. взять любую строку из 9 ячеек как **трафарет** для строк данных
   (клонируются стиль, границы, ширины колонок);
3. нормализовать трафарет: убрать вертикальный текст и фиксированную
   высоту (артефакты ГОСТ-шаблона);
4. для каждой группы `(линия → категория)` писать под-заголовок (объединение
   9 ячеек через `HorizontalMerge`), затем строки данных с нумерацией;
5. неиспользованные зарезервированные строки удалить.

Колонки (ГОСТ): `Поз. | Наименование | Тип/марка | Код | Поставщик |
Ед.изм. | Кол. | Масса 1 ед., кг | Примечание`.

Стиль каждой ячейки (шрифт, размер, выравнивание) наследуется от
эталонного трафарета, чтобы все строки выглядели как первая строка
данных шаблона.

## 9. Кэширование (`ScanCache`)

In-memory кэш результата сканирования **на одну сессию AutoCAD**
(не сохраняется на диск). Один слот (пользователь почти всегда работает
с одним проектом). Ключ — папка проекта; «отпечаток» — имя + размер +
время изменения каждого DWG плюс путь активного документа.

> Важно: если открыт хоть один документ, кэш **не используется** —
> mtime файла не знает про несохранённые правки в памяти, поэтому
> делается свежее чтение, чтобы спецификация отражала экран.

## 10. Настройки (`PluginSettings`)

Хранятся в `%APPDATA%\PipingSpecPlugin\settings.json`.

- Схема версионируется (`CurrentSchemaVersion = 4`) с forward-only
  миграциями (`Upgrade`) — паттерн «миграций БД».
- Forward-совместима: неизвестные поля игнорируются, отсутствующие
  берут значения по умолчанию.
- Повреждённый файл никогда не блокирует плагин — возвращается дефолт.

Сохраняются: путь шаблона, последняя папка вывода, область (`proj`/`dwg`),
группировка по линии, правила исключения, выбранные/известные
статусы/категории/линии, флаги «открывать в Word», «не группировать»
и «проверять обновления».

---

## 10a. Авто-обновление (`Update/`)

Плагин проверяет GitHub Releases на наличие новой версии при загрузке.

- **Триггер** — `PluginBootstrap.Initialize` запускает фоновую задачу
  (fire-and-forget, не блокирует загрузку AutoCAD). Honours флаг
  `PluginSettings.CheckForUpdates` (по умолчанию вкл.).
- **`UpdateChecker`** — чистая логика: парсит JSON релиза GitHub и
  сравнивает версии (`NormalizeVersion`/`Compare`). Полностью покрыта
  юнит-тестами, без сети и AutoCAD-типов.
- **`UpdateService`** — сетевая обёртка: `HttpClient` к
  `repos/IvanGelenko/specgen-net/releases/latest`, скачивание
  `PipingSpecPlugin-Setup.exe` во временную папку, запуск установщика.
  Любой сбой (офлайн, rate-limit, битый ответ) → тихо «нет обновлений».
- **`UpdateWindow`** (WPF) — уведомление «текущая → новая» + заметки
  релиза. «Обновить» скачивает и запускает установщик; т.к. AutoCAD
  держит DLL залоченной всю сессию, установка завершается **после
  закрытия AutoCAD** (окно об этом предупреждает). Хостится через
  `WindowInteropHelper.Owner = AcadApp.MainWindow.Handle`.
- **Версия** берётся из `AssemblyVersion` (штампуется `build.cmd` из
  файла `VERSION` как `X.Y.Z.0`). Релиз должен иметь тег `vX.Y.Z` и
  ассет `PipingSpecPlugin-Setup.exe`.

## 11. Слой UI

- **`SpecPickerWindow`** (WPF) — окно выбора фильтров. Питается
  `ProjectFacts` (статусы/категории/линии с количествами). Возвращает
  `SpecPickerResult`. Хостится через
  `WindowInteropHelper.Owner = AcadApp.MainWindow.Handle` + `ShowDialog()`.
  При запуске через кнопку область фиксируется (`forcedScope`).
- **`ProgressWindow`** (WPF) — модальный прогресс сканирования с
  поддержкой отмены (`IsCancelled`) и индикатором.

> AutoCAD 2025+ `Application.ShowModalWindow` принимает только `Uri`,
> не сконструированный `Window`. Поэтому окна показываются через
> `WindowInteropHelper` + `ShowDialog`, а не через этот API.

## 12. Сборка, загрузка, эксплуатация

### Сборка

```powershell
msbuild PipingSpecPlugin.sln /p:Configuration=Release
# нестандартный путь установки AutoCAD:
msbuild PipingSpecPlugin.sln /p:Configuration=Release /p:AcadInstallDir="D:\Autodesk\AutoCAD 2026"
```

`dotnet build` тоже работает (на машине только .NET 9 SDK, но он
таргетит net8.0 без проблем).

### Квирки сборки

- `GenerateAssemblyInfo=false` — рукописный `AssemblyInfo.cs` с
  `CommandClass`/`ExtensionApplication` не должен конфликтовать с
  авто-генерируемым.
- `Application` неоднозначен между `Autodesk.AutoCAD.ApplicationServices`
  и `System.Windows.Forms` — всегда алиасить (`using AcadApp = …`).
- `NoWarn=CA1416` — глушит анализатор платформенной совместимости для
  WinForms/WPF (всё равно только Windows).

### Загрузка и перезагрузка

После `NETLOAD` AutoCAD **блокирует** `PipingSpecPlugin.dll` до конца
сессии. Повторный билд в `bin/Release/` падает с `MSB3026`. Обходы:
закрыть AutoCAD перед ребилдом **или** билдить в версионированную папку
`bin/Release-vN.M/`. Чтобы подгрузить обновлённую DLL — **перезапустить
AutoCAD** (горячей перезагрузки .NET-плагинов нет). Попытка `NETLOAD`
другой копии той же сборки → `FileLoadException: Assembly with same name
is already loaded`.

### Диагностика прогона

- `%APPDATA%\PipingSpecPlugin\last-run.log` — полный трейс последнего
  прогона: число найденных компонентов, исключённые штуцера, топология,
  список гибов и их сворачивание, по-строчные дампы труб по линиям,
  причины отсева (`DropReasons`). Первое место, куда смотреть при
  «деталь не попала в спецификацию» / «короткий метраж».

## 13. Сводка архитектурных решений (не пересматривать)

- **Источник истины** — живая модель Plant 3D через `PnP*Mgd`, а не
  SQLite-снимок `Piping.dcf`.
- **Функциональность** — статусы, категории, линии, исключение спутников
  арматуры / оборудования / коннекторов, группировка по линии, контроль
  веса.
- **Лента** — нативно через `Autodesk.Windows.RibbonControl`, без `.cuix`.
- **Настройки** — `settings.json` в `%APPDATA%\PipingSpecPlugin`.
- **Фильтрация области dwg** — строго по `SourceDwgPath`, никогда по
  `PnPID` (rowId живут в drawing-local пространстве имён, один int
  именует разные детали в разных файлах).
